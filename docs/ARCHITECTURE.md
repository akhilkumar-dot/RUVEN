# FounderBridge Architecture

## System Overview

FounderBridge is a modular monolith built on Spring Boot 3 (Java 21) with a Next.js 14 frontend.
The "monolith" is intentional: one deployable unit per environment simplifies ops while the
package-per-module structure preserves clean boundaries and enables future extraction.

## High-Level Diagram

```
Browser (Next.js PWA)
    |-- REST /api/v1 (JSON, JWT Bearer)
    |-- STOMP/WebSocket ws://.../ws (chat, notifications)
    |-- Presigned S3 URLs (direct upload to MinIO/R2)
    v
Spring Boot Application (backend/)
    |-- Spring Security 6 (JWT filter chain)
    |-- Modules (packages): auth, users, companies, jobs, social, discover,
    |                        ideas, meetups, messaging, workspace, billing,
    |                        ads, notifications, media, admin
    |-- PostgreSQL 16 (Flyway migrations)
    |-- Redis (rate limits, token deny-list, presence, cache)
    |-- S3-compatible (MinIO local / Cloudflare R2 prod)
    |-- Email provider (MailHog dev / Resend prod)
    |-- Razorpay (webhooks inbound)
```

## API Design

- Base path: /api/v1
- Auth: Bearer JWT access token (15 min). Refresh via POST /api/v1/auth/refresh (reads HttpOnly cookie).
- Errors: RFC 7807 application/problem+json with stable "code" field.
- Pagination: cursor-based (?cursor=&limit=).
- OpenAPI 3.1: generated by springdoc-openapi, committed to docs/openapi.yaml.

## Data Flow: Auth

1. User submits email + password to POST /api/v1/auth/login
2. Server validates Argon2id hash, issues:
   - Access JWT (15 min, signed with RS256)
   - Refresh token (random 256-bit, hashed with SHA-256 for storage, set in HttpOnly cookie)
3. Client stores access JWT in memory (not localStorage).
4. On 401, client POSTs /api/v1/auth/refresh (refresh token read from cookie).
5. New refresh token issued (old one revoked). If old token already revoked -> revoke family.

## Data Flow: Media Upload

1. Client POSTs /api/v1/media/presign {purpose, contentType, filename}
2. Server checks ownership, plan limits, returns {uploadUrl, mediaId, key}
3. Client PUTs directly to MinIO/R2 using uploadUrl
4. Client POSTs /api/v1/media/{mediaId}/confirm
5. Server: magic-bytes MIME check, image re-encode + EXIF strip, mark media_asset as READY
6. media_asset.bucket_key is stored; never a direct URL in DB (always generated on demand)

## WebSocket (STOMP)

Endpoint: /ws (HTTP upgrade)
Auth: JWT passed as query param or CONNECT header (checked by ChannelInterceptor)

Topics:
- /user/queue/messages   (personal message delivery)
- /user/queue/notifications  (personal notification delivery)
- /topic/typing.{conversationId}  (typing indicator, TTL 3s)

## Infrastructure

Local dev: docker-compose.yml
  - postgres:16-alpine
  - redis:7-alpine
  - minio (S3-compatible)
  - mailhog (SMTP + web UI)
  - backend (Spring Boot)
  - web (Next.js)

Production: Railway
  - Managed PostgreSQL (Railway)
  - Managed Redis (Railway)
  - Docker image for backend
  - Docker image for web
  - Cloudflare R2 for object storage
  - Resend for email
